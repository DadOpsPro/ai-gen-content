How OpenAI Built a Secure Windows Sandbox for Codex Agents

When OpenAI deployed their Codex autonomous coding agents, they faced a critical challenge: how do you let an AI execute arbitrary code on Windows while preventing it from compromising the host system? Their solution combines Windows security primitives—Security Identifiers (SIDs), Access Control Lists (ACLs), restricted tokens, and dedicated sandbox accounts—into a defense-in-depth architecture that balances isolation with real developer workflows.

This guide walks you through implementing similar sandbox techniques for your own AI agent systems or automated code execution environments.

Why This Matters

Autonomous coding agents represent both tremendous productivity gains and significant security risks. When you allow an AI to write and execute code, you're essentially giving it the keys to your system. Consider these scenarios:

  • Malicious code injection: An AI could be manipulated through prompt injection to execute harmful commands
  • Accidental destruction: Even well-intentioned code might delete critical files or modify system configurations
  • Data exfiltration: An unrestricted agent could access and transmit sensitive information
  • Privilege escalation: Without proper containment, agent processes could gain elevated system access

    • OpenAI's Codex sandbox architecture addresses these risks by treating the AI agent as an untrusted entity from the operating system's perspective, regardless of the trust placed in the AI model itself. This principle—never trust, always verify—is fundamental to building secure AI agent systems.

    Step-by-Step Instructions

    Step 1: Create a Dedicated Sandbox User Account

    The foundation of OpenAI's approach starts with isolated user accounts. Each agent session runs under a dedicated, heavily restricted account rather than the host user's context. 

    # Create a sandbox user with minimal privileges
$sandboxPassword = ConvertTo-SecureString "$(New-Guid)" -AsPlainText -Force
$sandboxUser = "CodexSandbox_$(Get-Random -Maximum 9999)"

New-LocalUser -Name $sandboxUser `
    -Password $sandboxPassword `
    -Description "Isolated sandbox account for AI agent execution" `
    -AccountNeverExpires `
    -PasswordNeverExpires `
    -UserMayNotChangePassword

# Remove from all default groups
Get-LocalGroup | ForEach-Object {
    Remove-LocalGroupMember -Group $_.Name -Member $sandboxUser -ErrorAction SilentlyContinue
}

# Add to a custom restricted group
New-LocalGroup -Name "AIAgentSandbox" -Description "Restricted group for AI agents" -ErrorAction SilentlyContinue
Add-LocalGroupMember -Group "AIAgentSandbox" -Member $sandboxUser

    This script creates a user account with a random GUID password, ensuring the account cannot be accessed interactively. The account is stripped of all default group memberships, eliminating inherited permissions.

    Step 2: Configure Restricted Token Generation

    Windows restricted tokens allow you to create process tokens with reduced privileges. OpenAI's design uses this to strip dangerous privileges even from the sandbox account.

HANDLE CreateRestrictedSandboxToken(HANDLE hBaseToken) {
    // Define SIDs to disable in the token
    std::vector disableSids;
    
    // Disable the Administrators group SID
    PSID pAdminSid = nullptr;
    SID_IDENTIFIER_AUTHORITY ntAuthority = SECURITY_NT_AUTHORITY;
    AllocateAndInitializeSid(&ntAuthority, 2,
        SECURITY_BUILTIN_DOMAIN_RID, DOMAIN_ALIAS_RID_ADMINS,
        0, 0, 0, 0, 0, 0, &pAdminSid);
    
    disableSids.push_back({pAdminSid, 0});
    
    // Define privileges to delete
    LUID_AND_ATTRIBUTES privilegesToDelete[] = {
        {{SE_DEBUG_NAME}, 0},
        {{SE_BACKUP_NAME}, 0},
        {{SE_RESTORE_NAME}, 0},
        {{SE_SHUTDOWN_NAME}, 0},
        {{SE_TAKE_OWNERSHIP_NAME}, 0}
    };
    
    // Create restricting SIDs (what the token CAN access)
    PSID pRestrictedSid = nullptr;
    ConvertStringSidToSidA("S-1-5-12", &pRestrictedSid); // Restricted Code SID
    
    SID_AND_ATTRIBUTES restrictingSids[] = {
        {pRestrictedSid, 0}
    };
    
    HANDLE hRestrictedToken = nullptr;
    BOOL success = CreateRestrictedToken(
        hBaseToken,
        DISABLE_MAX_PRIVILEGE,  // Remove all privileges not explicitly needed
        static_cast(disableSids.size()),
        disableSids.data(),
        0,                      // No privileges to delete explicitly
        nullptr,
        1,                      // One restricting SID
        restrictingSids,
        &hRestrictedToken
    );
    
    // Cleanup allocated SIDs
    FreeSid(pAdminSid);
    LocalFree(pRestrictedSid);
    
    return success ? hRestrictedToken : nullptr;
}

    This function creates a token that cannot exercise administrative privileges, even if the base account somehow acquires them. The DISABLE_MAX_PRIVILEGE flag is crucial—it strips all privileges except those absolutely necessary for basic process execution.

    Step 3: Set Up File System ACLs for the Sandbox Directory

    The sandbox needs a workspace, but access must be tightly controlled. OpenAI's approach creates an isolated directory hierarchy with explicit deny rules preventing escape. 

    # Create sandbox workspace
$sandboxRoot = "C:\AgentSandbox\$sandboxUser"
New-Item -Path $sandboxRoot -ItemType Directory -Force

# Create SDDL string for restrictive permissions
# Owner: SYSTEM, Full control for sandbox user only within this tree
$sddl = "O:SYG:SYD:PAI(A;OICI;FA;;;$((Get-LocalUser $sandboxUser).SID))(A;OICI;FA;;;SY)"

# Apply the security descriptor
$acl = Get-Acl $sandboxRoot
$acl.SetSecurityDescriptorSddlForm($sddl)
Set-Acl -Path $sandboxRoot -AclObject $acl

# Explicitly deny access to sensitive system locations
$denyPaths = @(
    "C:\Windows\System32",
    "C:\Program Files",
    "C:\Users",
    "$env:USERPROFILE"
)

foreach ($path in $denyPaths) {
    $rule = New-Object System.Security.AccessControl.FileSystemAccessRule(
        $sandboxUser,
        "FullControl",
        "ContainerInherit,ObjectInherit",
        "None",
        "Deny"
    )
    
    $acl = Get-Acl $path
    $acl.AddAccessRule($rule)
    Set-Acl -Path $path -AclObject $acl
}

    Step 4: Implement Job Object Restrictions

    Windows Job Objects provide process-level containment. OpenAI uses these to limit resource consumption and prevent the agent from spawning unrestricted child processes. 

    HANDLE CreateSandboxJobObject() {
    HANDLE hJob = CreateJobObjectW(nullptr, L"CodexAgentSandbox");
    if (!hJob) return nullptr;
    
    // Configure basic limits
    JOBOBJECT_BASIC_LIMIT_INFORMATION basicLimits = {};
    basicLimits.LimitFlags = 
        JOB_OBJECT_LIMIT_ACTIVE_PROCESS |      // Limit number of processes
        JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE |   // Kill all processes when job closes
        JOB_OBJECT_LIMIT_DIE_ON_UNHANDLED_EXCEPTION;
    basicLimits.ActiveProcessLimit = 10;       // Max 10 concurrent processes
    
    SetInformationJobObject(hJob, JobObjectBasicLimitInformation,
        &basicLimits, sizeof(basicLimits));
    
    // Configure UI restrictions
    JOBOBJECT_BASIC_UI_RESTRICTIONS uiLimits = {};
    uiLimits.UIRestrictionsClass = 
        JOB_OBJECT_UILIMIT_DESKTOP |           // Cannot switch desktops
        JOB_OBJECT_UILIMIT_EXITWINDOWS |       // Cannot shutdown
        JOB_OBJECT_UILIMIT_GLOBALATOMS |       // Cannot access global atoms
        JOB_OBJECT_UILIMIT_HANDLES |           // Cannot use USER handles
        JOB_OBJECT_UILIMIT_SYSTEMPARAMETERS;   // Cannot change system params
    
    SetInformationJobObject(hJob, JobObjectBasicUIRestrictions,
        &uiLimits, sizeof(uiLimits));
    
    // Configure network restrictions (Windows 10+)
    JOBOBJECT_NET_RATE_CONTROL_INFORMATION netLimits = {};
    netLimits.ControlFlags = JOB_OBJECT_NET_RATE_CONTROL_ENABLE;
    netLimits.MaxBandwidth = 1024 * 1024;  // 1 MB/s max
    
    SetInformationJobObject(hJob, JobObjectNetRateControlInformation,
        &netLimits, sizeof(netLimits));
    
    return hJob;
}

    Step 5: Launch the Sandboxed Agent Process

    Bringing all components together, here's how to launch a process within the complete sandbox: 

    bool LaunchSandboxedAgent(const wchar_t* commandLine, const wchar_t* workingDir) {
    // Create the sandbox user token
    HANDLE hUserToken = LogonUserW(
        L"CodexSandbox_1234",  // Sandbox username
        L".",                   // Local machine
        L"",    // Generated password
        LOGON32_LOGON_BATCH,
        LOGON32_PROVIDER_DEFAULT,
        &hUserToken
    );
    
    // Create restricted token
    HANDLE hRestrictedToken = CreateRestrictedSandboxToken(hUserToken);
    
    // Create job object
    HANDLE hJob = CreateSandboxJobObject();
    
    // Prepare process creation
    STARTUPINFOW si = {sizeof(si)};
    PROCESS_INFORMATION pi = {};
    
    // Create process suspended so we can assign to job
    BOOL created = CreateProcessAsUserW(
        hRestrictedToken,
        nullptr,
        const_cast(commandLine),
        nullptr,
        nullptr,
        FALSE,
        CREATE_SUSPENDED | CREATE_NEW_CONSOLE,
        nullptr,
        workingDir,
        &si,
        &pi
    );
    
    if (created) {
        // Assign to job object before resuming
        AssignProcessToJobObject(hJob, pi.hProcess);
        
        // Now resume the process
        ResumeThread(pi.hThread);
        
        CloseHandle(pi.hThread);
    }
    
    // Store handles for later cleanup
    // hJob, pi.hProcess, hRestrictedToken, hUserToken
    
    return created != FALSE;
}

    Common Pitfalls & How to Avoid Them

    Pitfall 1: Inherited Handle Leakage

    Child processes can inherit handles from the parent, potentially bypassing sandbox restrictions. Solution: Always set bInheritHandles to FALSE in CreateProcessAsUser, and use PROC_THREAD_ATTRIBUTE_HANDLE_LIST to explicitly control handle inheritance when needed.

    Pitfall 2: Token Group Membership Caching

    Windows caches group membership in tokens. Changes to group membership don't affect existing sessions. Solution: Generate fresh tokens for each agent session rather than reusing tokens across multiple executions.

    Pitfall 3: Symlink and Junction Escapes

    Agents might create symbolic links or junctions pointing outside the sandbox. Solution: Disable symlink creation privileges and use Windows Defender Application Control policies to block junction creation for sandbox accounts.

    Pitfall 4: Named Object Namespace Pollution

    Agents can create named objects (mutexes, events) that persist beyond their session. Solution: Use CreatePrivateNamespace to isolate the agent's named objects: 

    HANDLE CreateIsolatedNamespace() {
    SECURITY_ATTRIBUTES sa = {sizeof(sa)};
    HANDLE hBoundary = CreateBoundaryDescriptorW(L"AgentBoundary", 0);
    
    PSID pSid;
    // Add sandbox user SID to boundary
    AddSIDToBoundaryDescriptor(&hBoundary, pSid);
    
    return CreatePrivateNamespaceW(&sa, hBoundary, L"AgentNamespace");
}

    Real-World Example: Secure Python Execution

    Here's a complete example demonstrating the sandbox executing a Python script from a Codex agent: 

    # Agent orchestrator script
function Invoke-SandboxedPythonAgent {
    param(
        [string]$PythonCode,
        [int]$TimeoutSeconds = 30
    )
    
    # Write code to sandbox directory
    $sandboxUser = Get-SandboxAccount
    $workDir = "C:\AgentSandbox\$($sandboxUser.Name)"
    $scriptPath = Join-Path $workDir "agent_task.py"
    
    Set-Content -Path $scriptPath -Value $PythonCode
    
    # Launch sandboxed Python
    $process = Start-SandboxedProcess `
        -Executable "python.exe" `
        -Arguments $scriptPath `
        -WorkingDirectory $workDir `
        -SandboxUser $sandboxUser `
        -JobLimits @{
            MemoryLimitMB = 512
            CpuRatePercent = 25
            MaxProcesses = 5
        }
    
    # Wait with timeout
    $completed = $process.WaitForExit($TimeoutSeconds * 1000)
    
    if (-not $completed) {
        Stop-Process -Id $process.Id -Force
        throw "Agent execution timed out"
    }
    
    # Return results from sandbox output file
    return Get-Content (Join-Path $workDir "output.json")
}
