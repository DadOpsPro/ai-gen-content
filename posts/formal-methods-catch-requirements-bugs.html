How to Use Formal Methods to Catch Requirements Bugs Before They Become Code Disasters

AWS found that 60% of software requirements contain critical bugs. Their solution isn't another AI tool — it's a 50-year-old logic engine called formal verification. Here's how to implement it in your testing workflow.

The most expensive bugs in software aren't in the code. They're in the requirements that guide the code's construction. When Amazon Web Services analyzed thousands of system specifications, they found defects lurking in nearly two-thirds of them — ambiguities, contradictions, and logical impossibilities that no amount of unit testing could ever catch.

Their fix wasn't more machine learning. It was temporal logic and model checking, mathematical techniques dating back to the 1970s. This guide shows you how to apply these battle-tested methods to your own requirements validation process.

Why This Matters

Requirements bugs are silent killers. By the time they manifest as production failures, fixing them costs 100x more than catching them during specification. Consider these scenarios:

  • A banking system requirement states "transactions must complete within 5 seconds" while another requires "all transactions must be verified by three separate services, each with a 3-second timeout"
  • An access control spec demands "users can only view their own data" but also states "managers can generate reports on all team members"
  • A distributed system requirement promises "exactly-once delivery" without specifying behavior during network partitions

    • Human reviewers miss these contradictions because they read requirements linearly, not logically. Formal methods convert natural language specs into mathematical models where contradictions become provably impossible states.

    AWS's internal tools, including their proprietary P language and TLA+ specifications, have prevented countless production incidents. The techniques they use are available to every development team.

    Step-by-Step Instructions

    Step 1: Extract Testable Properties from Natural Language Requirements

    Before any tool can verify requirements, you must translate them from prose into formal properties. This isn't about rewriting everything — focus on safety properties (things that must never happen) and liveness properties (things that must eventually happen).

    Start with a real requirement: 

    REQUIREMENT REQ-AUTH-001:
"Users must be logged out after 30 minutes of inactivity. 
Users with active sessions cannot be logged out by administrators 
unless there is a security incident. Premium users never 
experience forced logouts during business hours."

    Extract the atomic propositions: 

    Define your atomic propositions as boolean variables
    
propositions = {
    "inactive_30min": "User has been inactive for 30 minutes",
    "logged_in": "User is currently logged in",
    "admin_logout": "Administrator initiates logout",
    "security_incident": "Security incident is active",
    "premium_user": "User has premium subscription",
    "business_hours": "Current time is within business hours",
    "forced_logout": "System forces user logout"
}

    Step 2: Convert Properties to Logical Formulas

    Now translate the requirement into formal logic. This is where contradictions become visible: 

    from z3 import *


    Create boolean variables
    
inactive_30min = Bool('inactive_30min')
logged_in = Bool('logged_in')
admin_logout = Bool('admin_logout')
security_incident = Bool('security_incident')
premium_user = Bool('premium_user')
business_hours = Bool('business_hours')
forced_logout = Bool('forced_logout')


    Create a solver instance
    
solver = Solver()


    Rule 1: 30 minutes of inactivity implies logout
    

    "Users must be logged out after 30 minutes of inactivity"
    
rule1 = Implies(inactive_30min, forced_logout)


    Rule 2: Active sessions block admin logout (unless security incident)
    

    "Users with active sessions cannot be logged out by administrators 
    

     unless there is a security incident"
    
rule2 = Implies(
    And(logged_in, admin_logout, Not(security_incident)),
    Not(forced_logout)
)


    Rule 3: Premium users protected during business hours
    

    "Premium users never experience forced logouts during business hours"
    
rule3 = Implies(
    And(premium_user, business_hours),
    Not(forced_logout)
)


    Add all rules to solver
    
solver.add(rule1)
solver.add(rule2)
solver.add(rule3)

    Step 3: Check for Contradictions Using the Z3 Solver

    Now test whether a scenario exists that satisfies all rules — and whether impossible scenarios are properly excluded: 

    def check_scenario(solver, scenario_name, conditions):
    """
    Check if a scenario is satisfiable given requirements.
    """
    solver.push()  # Save current state
    
    for condition in conditions:
        solver.add(condition)
    
    result = solver.check()
    
    if result == sat:
        print(f"✓ {scenario_name}: SATISFIABLE")
        model = solver.model()
        print(f"  Model: {model}")
    elif result == unsat:
        print(f"✗ {scenario_name}: CONTRADICTION FOUND")
    else:
        print(f"? {scenario_name}: UNKNOWN")
    
    solver.pop()  # Restore state
    return result


    Test Scenario: Premium user inactive for 30 min during business hours
    
print("Testing requirement consistency...\n")

    

    scenario1 = check_scenario(
    solver,
    "Premium user timeout during business hours",
    [premium_user, business_hours, inactive_30min, logged_in]
)
    Expected Output: 
    Testing requirement consistency...

    

    ✗ Premium user timeout during business hours: CONTRADICTION FOUND

    The solver found a bug: Rule 1 requires logout after inactivity, but Rule 3 prohibits forced logout for premium users during business hours. The requirements are internally inconsistent.

    Step 4: Model State Transitions with TLA+

    For complex systems, static logic checking isn't enough. You need to verify that valid states can transition correctly over time. TLA+ excels at this.

    Create a file SessionManager.tla: 

    ---------------------------- MODULE SessionManager ----------------------------
EXTENDS Integers, Sequences

    

    CONSTANTS Users, MaxInactiveMinutes

    

    VARIABLES 
    sessions,        \* Map: User -> {active, inactive, logged_out}
    inactiveTime,    \* Map: User -> Integer (minutes inactive)
    securityMode     \* Boolean: security incident active

    

    TypeInvariant ==
    /\ sessions \in [Users -> {"active", "inactive", "logged_out"}]
    /\ inactiveTime \in [Users -> 0..MaxInactiveMinutes]
    /\ securityMode \in BOOLEAN

    

    Init ==
    /\ sessions = [u \in Users |-> "logged_out"]
    /\ inactiveTime = [u \in Users |-> 0]
    /\ securityMode = FALSE

    

    \* User logs in
Login(user) ==
    /\ sessions[user] = "logged_out"
    /\ sessions' = [sessions EXCEPT ![user] = "active"]
    /\ inactiveTime' = [inactiveTime EXCEPT ![user] = 0]
    /\ UNCHANGED securityMode

    

    \* Time passes, user becomes inactive
BecomeInactive(user) ==
    /\ sessions[user] = "active"
    /\ sessions' = [sessions EXCEPT ![user] = "inactive"]
    /\ UNCHANGED <>

    

    \* Inactive time increments
TimePass(user) ==
    /\ sessions[user] = "inactive"
    /\ inactiveTime[user] < MaxInactiveMinutes
    /\ inactiveTime' = [inactiveTime EXCEPT ![user] = @ + 1]
    /\ UNCHANGED <>

    

    \* Auto-logout after timeout
TimeoutLogout(user) ==
    /\ sessions[user] = "inactive"
    /\ inactiveTime[user] >= MaxInactiveMinutes
    /\ sessions' = [sessions EXCEPT ![user] = "logged_out"]
    /\ UNCHANGED <>

    

    \* Safety Property: No user with active session gets logged out 
\* (unless security mode)
SafetyProperty ==
    \A u \in Users:
        (sessions[u] = "active" /\ ~securityMode) => 
            sessions'[u] # "logged_out"

    

    Next ==
    \E u \in Users:
        \/ Login(u)
        \/ BecomeInactive(u)
        \/ TimePass(u)
        \/ TimeoutLogout(u)

    

    Spec == Init /\ [][Next]_<>

    

    ===============================================================================

    Run the model checker in the TLA+ Toolbox to verify all state transitions preserve safety properties.

    Common Pitfalls & How to Avoid Them

    Pitfall 1: Over-specification Writing overly detailed formal specs for every requirement wastes time. Focus on:
  • Security boundaries
  • State transitions
  • Resource limits
  • Timing constraints
    • Pitfall 2: Ignoring the "Happy Path" Assumption Requirements often implicitly assume everything works. Always add failure conditions: 
    Bad: Only models success
    
rule = Implies(request_sent, response_received)


    Good: Models timeouts and failures
    
rule = Implies(
    request_sent,
    Or(
        response_received,
        timeout_occurred,
        connection_failed
    )
)
    Pitfall 3: Treating Verification as Testing Formal methods don't replace testing — they find different bugs. Model checkers prove properties hold across all possible states, while tests verify specific scenarios. Pitfall 4: Ignoring Tool Limitations Z3 and TLA+ can face state explosion on large models. Constrain your state space: 
    Limit numeric ranges to prevent explosion
    
solver.add(timeout_seconds >= 0)
solver.add(timeout_seconds <= 300)  # Reasonable upper bound

    Real-World Example: E-Commerce Checkout Requirements

    Let's verify a real checkout system specification: 

    REQ-CHECKOUT-001: Cart total must equal sum of item prices
REQ-CHECKOUT-002: Discounts cannot exceed 50% of cart total
REQ-CHECKOUT-003: Free shipping applies when cart total exceeds $50
REQ-CHECKOUT-004: Discount codes can provide free shipping on any order

    from z3 import *


    Create the solver
    
s = Solver()


    Define variables
    
cart_total = Real('cart_total')
item_sum = Real('item_sum')
discount_amount = Real('discount_amount')
final_total = Real('final_total')
shipping_cost = Real('shipping_cost')
free_shipping = Bool('free_shipping')
discount_code_applied = Bool('discount_code_applied')


    REQ-001: Cart total equals item sum
    
s.add(cart_total == item_sum)


    REQ-002: Discount limit
    
s.add(discount_amount <= cart_total * 0.5)
s.add(discount_amount >= 0)


    REQ-003: Free shipping threshold
    
s.add(Implies(cart_total > 50, free_shipping))


    REQ-004: Discount codes give free shipping
    
s.add(Implies(discount_code_applied, free_shipping))


    Final total calculation
    
s.add(final_total == cart_total - discount_amount + 
      If(free_shipping, 0, shipping_cost))


    Test: Can we have negative final total?
    
s.push()
s.add(final_total < 0)
s.add(cart_total > 0)
s.add(shipping_cost >= 0)

    

    if s.check() == sat:
    print("BUG: Negative checkout total possible!")
    print(s.model())
else:
    print("✓ Negative totals correctly prevented")
s.pop()


    Test: What if discount equals exactly cart total with free shipping?
    
s.push()
s.add(discount_amount == cart_total * 0.5)
s.add(cart_total == 40)  # Below free shipping threshold
s.add(discount_code_applied == False)
s.add(shipping_cost == 10)

    

    if s.check() == sat:
    print("\nScenario: $40 cart, 50% discount, no code")
    m = s.model()
    print(f"  Final total: ${m[final_total]}")
    print(f"  Free shipping: {m[free_shipping]}")
    Output: 
    ✓ Negative totals correctly prevented

    

    Scenario: $40 cart, 50% discount, no code
  Final total: $30
  Free shipping: False

    The requirements are consistent, but we've also revealed that a $40 cart with 50% discount pays $30 (including $10 shipping) — potentially surprising to customers who expect to pay $20.
